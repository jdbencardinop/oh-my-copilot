05 — DeepSeek superagent, Google's Elephant-Goldfish Model, and Microsoft's TokenEconomizer

This report covers two projects the user asked to add: DeepSeek's dsh-superagent-prototype and Google's elephant-goldfish-model (EGM), and Microsoft's TokenEconomizer. For each one, it answers three questions:

  1. What does OMC already have?
  2. What belongs in another layer, such as an orchestrator, a service, or the harness itself?
  3. What can OMC bring in?

Summary

  • EGM is the stronger candidate for OMC. It is a set of skills and agent files and works as a plugin. It already ships an experimental Copilot CLI adapter and an OMP plugin install. Its core idea also fits our layer: one agent keeps the full context and drafts the design (the "elephant"), and fresh subagents with no context review it (the "goldfish"). OMC should use EGM directly and reuse its patterns, not copy its skills.
  • dsh-superagent is mostly a different layer. It is a long-running service. It listens to GitHub and Feishu, decides which requests to take, opens tickets, and runs one worker session per ticket. That is orchestrator or service work, close to T3 Code or Copilot's cloud agent. Its prompt rules, however, carry over well: ask for attention only when needed, stop at defined scope limits, report delivery honestly, and keep a person's pause in force.
  • TokenEconomizer is in our layer and overlaps the most. It is a Copilot CLI plugin built on hooks that cuts cost by learning across a repository's sessions. Its loop guard, learned repo facts, and tool pruning sit next to OMC's stream rules, rules, and deferred per-model tool profiles. OMC should coexist with it and borrow its methods, not rebuild it.
  • OMC already covers part of all three. The reviewer agent is a fresh-context reviewer, rules give the model written policy, and the commit skill and anchored edits support delivery. What OMC lacks: design-stage review, a drift check from docs to code, and a "low-attention" working style.

dsh-superagent in brief

dsh-superagent is a research prototype that runs as a plugin inside DeepSeek Harness (DSH). It is not an official DeepSeek product. It acts as an automated team member for one GitHub repository.

  • Flow. A Source (GitHub or Feishu) emits Triggers. An Eval step decides whether a batch of triggers asks for new work. On accept, it creates a Ticket with a Mandate: what the agent may do and why. An Executor runs one DSH session and one directory per ticket, and replies on the original thread. (001 Domain)
  • Two roles. The main session (the orchestrator) only routes, with routing notes of 30 words or fewer. The workers read sources, implement, and verify. The orchestrator has 14 tools; each worker has 6, such as orchestrator_report and orchestrator_trigger_handback.
  • No waiting. A guard refuses sleep, shell timeouts over 30 seconds, and job waits over 5 seconds in the main session. Reports arrive as messages instead.
  • Philosophy: minimize human attention. The agent acts only when asked or when a written rule allows it. Proactive rules start in a record-only mode. It speaks only when a person must act, and asks one structured question at a time. (000 Philosophy)
  • Scope rules. A worker finishes focused changes through review and CI. It stops when a change would break caller expectations, change module responsibilities, or redesign several modules. It then leaves an explicitly incomplete draft PR and names the blocker.
  • Honest delivery. Opening a PR does not mean it is ready. A UI change needs real before and after screenshots. The agent never merges its own work, and enables auto-merge only under configured limits.
  • Per-role models (src/app/role-models.ts), a web panel that shows only items that need a person, and an agent-guided SETUP.md.

EGM in brief

EGM's motto is "design with an elephant, review with a goldfish". A context-rich agent and the user write a spec. Then zero-context subagents stress-test it before any code is written.

  • Skills: egm-bootstrap (folder READMEs), egm-brainstorm (concepts_brief.md), egm-draft (design_draft.md, section by section), egm-review (staged subflows), egm-review-loop (review, resolve, repeat), egm-resolve, and egm-drift-report.
  • Reviewer personas: design critic, zoom out, comprehension, implementation readiness, structural, style, codebase details, inventive catalyst, plus a synthesizer.
  • A strict review contract. Each reviewer runs in a new child that receives only the target, the line ranges, its persona, the standards, and a reading list. It never gets the conversation. If the harness cannot start a fresh subagent, the review stops: "a review in the same context is not a Goldfish review".
  • Anti-sycophancy rules. Critique comes first. The rules ban flattery and apologies. Each gate asks exactly one question. Large outputs go to files, not the chat.
  • Drift report. For each design doc or README, the skill finds the related code and reports only differences: missing features, incomplete models, hard-coded shortcuts, and architectural divergence.
  • Many harnesses, one skill text. Claude Code, Codex, Antigravity, OMP and others install the same plugin. (harnesses.md)

EGM on Copilot CLI today

EGM's Copilot guide labels the adapter experimental and says workflow execution and reviewer isolation are unverified.

  • It loads through copilot --plugin-dir "$EGM_ROOT" --agent egm:egm. The entry agent maps each persona to a native profile, such as egm:egm-design. Reviewers get only read and search and use include-custom-instructions: false.
  • An offline test with CLI 1.0.82 confirmed that eight profiles and seven skills are discovered, using a disposable COPILOT_HOME, without calling a model.
  • Its guide notes that copilot plugin install from a local path is unverified, and that a separate context window does not prove instructions or memory are isolated.

TokenEconomizer in brief

TokenEconomizer ("experience-driven black-box cost control for coding agents") makes an agent cheaper in repositories you use often. It does not change the agent. It learns from earlier sessions in the same repository and uses that to cut waste in later ones. (README, plugin guide)

  • Micro-skills (off by default). It learns repository facts, such as "use python -m pytest here" or "run this build step first". Facts come from failures that repeat across sessions and from a model that reviews recent sessions every 3 sessions. A fact is injected at session start once three sessions confirm it, and dropped when later sessions contradict it.
  • Tool pruning (on). Tools unused over 10 prompts across 2 sessions, or over 5 sessions, are left out of later sessions through the agent's own settings. One command restores them.
  • Loop guard (on). When a turn keeps hitting the same failures, a judge model checks whether it is stuck. At 0.7 confidence or more, it adds one redirect note per turn. If the turn is still stuck, it tells the person how to stop it; it never stops a turn itself.
  • Cost as billed. It counts cached tokens at cache prices and includes its own model calls in a per-session ledger, shown by status.
  • Reported results. On 277 SWE-Bench tasks across six repositories, mean cost fell 18.4–30.9% for five agent and model combinations, and Pass@1 rose in four of five. These are the authors' numbers.
  • Hosts. Claude Code, Codex, Copilot CLI and Pi are supported; opencode, Cursor Agent and Hermes Agent are experimental. One Python core sits behind a thin adapter per host.

TokenEconomizer on Copilot CLI today

  • Install: copilot plugin marketplace add <absolute clone path>, then copilot plugin install tokeneconomizer@tokeneconomizer. Tested on Copilot CLI 1.0.83 to 1.0.102; OMC runs 1.0.105, which is untested.
  • Hooks: SessionStart, UserPromptSubmit, PostToolUse, PostToolUseFailure, Stop and SessionEnd, all calling one Python script. Facts enter as additionalContext.
  • Tool pruning is coarse on Copilot. Copilot has no persistent per-tool filter: --excluded-tools is a launch flag, and permissions.deny refuses a call but still sends the tool's schema. The only working lever was disabledMcpServers in the repository's .github/copilot/settings.local.json, which removes a whole MCP server, such as the built-in GitHub server. It applies only in a trusted folder.
  • Its own model calls run through copilot -p, with the cheapest capable model.
  • It cannot stop a Copilot turn: Copilot ignores continue: false from hooks.
  • State lives in ~/.tokeneconomizer, outside COPILOT_HOME. A disposable test must also set TOKENECONOMIZER_HOME.
  • Evidence is thin for Copilot: the real-model checks used one model, Claude Haiku 4.5, over BYOK.

Recommended additions

These are proposals, not decisions, and are listed in suggested order.

  1. Recommend EGM alongside OMC. Add a short install note and test it in the disposable COPILOT_HOME. Check for agent name conflicts with oh-my-copilot:reviewer. EGM already asks whether reviewer isolation holds on Copilot, so test that before relying on it.
  2. Drift-report skill. A read-only skill that compares design docs or READMEs with the code and reports only the differences. It complements EGM rather than duplicating its design flow.
  3. Honest isolation in the reviewer. Add include-custom-instructions: false if Copilot honors it for plugin agents, and state the limits in the reviewer's output.
  4. Low-attention rule pack. An opt-in rule set based on dsh's prompts: confirm once, ask one question, stop at named scope limits, do not call a draft ready, and keep a person's pause.
  5. Dry-run mode for stream rules. Log matches without aborting so users can tune patterns safely.
  6. Offline discovery test in CI, following EGM's SDK RPC probe. Use it for packaging.
  7. Test TokenEconomizer next to OMC in a disposable COPILOT_HOME with its own TOKENECONOMIZER_HOME. Check that both plugins' prompt and session-start context coexist, and that its MCP pruning does not touch OMC. If it works, recommend it rather than build cost control.
  8. Loop-guard ideas for stream rules. Add a "same failure repeated" trigger and a "redirect once, then tell the person" limit.
  9. Evidence-based defaults for per-model tool profiles (item 10), using TokenEconomizer's unused-tool thresholds and restore command.

Not recommended

  • Rebuilding dsh-superagent inside OMC. Admission, tickets, and multi-session routing need a long-running process and Source connectors. That belongs in an orchestrator. OMC can make sessions behave better when an orchestrator runs them.
  • Rebuilding TokenEconomizer's cost control. It already supports Copilot and is backed by a paper. OMC should not ship a second session-learning system that injects competing context.
  • Forking EGM's skills. EGM keeps one skill text for every harness and is still evolving. Copying it would create drift. OMC should integrate with it and fill gaps.
